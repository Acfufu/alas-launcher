§1 方法论

轮次结构：重审五轮的范围依次为 ①后端生命周期 / ②托盘菜单 + 跨语言契约 / ③配置构建 + 跨文件一致性 / ④并发红队 + 平台差异 / ⑤执行走查 + 构建验证。每轮 2 名审核员、findings-only（禁止编辑）、每条发现必须附 file:line 证据与触发推演、按 P0/P1/P2 定级、限额防凑数。

轮间修复：主审逐条反证（对照上下游代码与依赖源码）后才动手修复；修复独立成批次提交，下一轮审核员看到的是修复后的树。

回归专责：从第 2 轮起，每轮固定安排一名审核员只审上一轮修复提交的全量 diff。该机制三轮连续抓到上轮修复自身引入的真问题（详见 §3），是本次最大单项方法论收益。

锁定源码核证：凡涉及依赖行为的主张（command-group 的 waitpid 语义、tauri 菜单 API 的主线程汇合、rfd 的线程约束），一律对照 Cargo.lock 实际锁定的版本的 registry 源码核实，不采信审核员引用的其它版本——本轮有一次引用与锁定版本不符（结论碰巧成立）与一次结论错误（见 §4）。

轻量收敛循环：重审结束后以轻量双审核迭代，发现收敛到纯文档级后再跑一轮零发现确认即终止（L4）。

第 4 轮 — 并发红队 / 平台差异 + R3 回归专责（11 条：1 P0 + 2 P1 + 8 P2）

P0：退出死锁——主线程 join ⟷ 轮询线程的主线程汇合

P0

tauri 菜单 API（MenuItem::with_id / set_menu / set_icon）从非主线程是「投递主线程 + rx.recv() 同步等待」（对照锁定的 tauri 2.5.1 源码证实——审核员引用的是 registry 里 2.11.5，结论碰巧一致）。退出处理运行期间事件循环不再泵消息：主线程 join 轮询线程 ⟷ 轮询线程正卡在菜单调用等主线程泵消息，循环等待，只能强杀——且强杀跳过全部后端清算。修复：join 移交 janitor 线程 + 3 秒有界等待（超时放弃继续清算、卡住线程随进程回收）；poll_once 入口与重建前双重 stop 复查把窗口压到 ms 级；两条「永不阻塞主线程」的不实注释修正。src/child_process.rs、src/tray.rs

§4 经反证否决的发现

「整组 try_wait 使早退检测退化为 60s 全额等待」——否决

误报

该主张认为 leader 死后 multiprocessing Manager 长期占组导致 try_wait 持续 None。对照 command-group 5.0.1 源码反证：waitpid(-pgid) 只匹配调用者自己的子进程，组内孙进程在 leader 死后即被 launchd/init 收养、从不计入——leader 退出后 ECHILD 立即到达，早退检测成立。Windows 侧更是 leader 语义。未修改。

另：R5 走查中「save_as IPC 被 ACL 拒绝」候选经审核员自行对照 tauri 2.5.1 ACL 逻辑证伪剔除（无 app-manifest 时 app 命令不受 ACL 门控）。引用版本与锁定版本不符一次（tauri 2.11.5 vs 2.5.1，结论碰巧成立）。

tauri capability/ACL 未配置（建议单独立项）：项目零 capability、无 CSP、release 带 devtools。save_as 靠「无 app-manifest 免检」旁路工作，安全姿态是隐式的而非声明的。加固需设计 capability 边界并回归 webui 的 saveAs 链路，不宜在本轮顺手动。

docs/ 目录被 .gitignore 忽略：docs/pr5885-implementation-plan.md 等四份 runbook 是未跟踪的本地文件，换机即失。是否豁免入库属仓库策略决定，本轮未动（仅修正了其中两处陈旧陈述）。

Windows 交叉编译本机不可验证：无 rustup/Windows target，CI 亦仅 macOS。R3/R4 的 Windows 侧改动（wincon feature、ESRCH_RAW、create_no_window×3）经静态读码 + 符号级核对（winapi docs.rs）验证，但属验证盲区——建议首次 Windows 出包前跑一次 cargo check --target x86_64-pc-windows-msvc。
