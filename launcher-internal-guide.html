ALAS Launcher 内部执行图解报告

面向初级开发者的图文解说：这个仓库（alas-launcher）自己内部是怎么执行的 —— 进程怎么拉起、状态怎么流转、异常怎么兜底、macOS 菜单栏怎么控制调度器
Tauri v2 / Rust 后台状态机 进程组管理 控制 API 补丁（HTTP） macOS 菜单栏 单实例 Win / macOS / Linux

0. 先看结论：这个仓库到底干了什么

30 秒速览。本报告是《ALAS 项目架构图解》的姊妹篇：那份报告讲「ALAS 本体 + 启动器」拼成机器人，这份只讲启动器仓库内部。

这个仓库（alas-launcher，Rust + Tauri）不是一个「带按钮的浏览器壳」。它真正的工作是四件事：

  • ①进程管家：找到 ALAS 目录 → 注入绿色版工具链环境变量 → 清理配置残留 → 拉取仓库更新 → 拉起 ALAS Web 后端子进程（gui.py 或 module.cli run web，按树形二选一）并验证它真的活在了正确的端口上 → 退出时把整棵进程树收掉。
  • ②后台状态机：一个三态（Stopped / Initializing / Running）生命周期，外加「用户意图」记录，用来区分「调度器是自己死的」还是「用户让它停的」——这是菜单栏状态行的语义基础。
  • ③双 UI 外壳：主窗口 WebView（导航到 ALAS 网页 + 注入 window.saveAs 接管文件保存）+ macOS 菜单栏托盘（轮询真实任务列表、一键启停调度器）。
  • ④控制通道：托盘启停调度器时，启动器调用控制 API 补丁注入的 HTTP 接口（POST /api/alas/alas/scheduler/start|stop——路径里两个 alas 不是笔误：前者是 API 路由前缀，后者是实例名，默认实例就叫 alas）——与 ALAS 网页共享同一个 ProcessManager，不碰任何游戏逻辑。
一句话总结：启动器 = 「准备环境 + 更新仓库 + 拉起并监护 Web 后端」的进程管家，外面套一层状态机，macOS 上再加一个能读任务列表、能通过控制 API 启停调度器的菜单栏。ALAS 本体在本报告中只作为右侧一个蓝色小方块出现——它的内部解剖请看《ALAS 项目架构图解》。

1. 全景图：启动器内部模块怎么分工

这张图是整份报告的地图。橙色 = 启动器自己的模块，蓝色 = ALAS（只露必要的接口），绿色 = 配置。

图 1：启动器内部全景。橙色方块全部是本仓库的模块；蓝色方块是 ALAS（本报告不展开）；虚线 = 跨边界弱耦合（读配置 / 探测 / 更新 / 控制调用）。

模块分层原则

  • 决策纯函数化：toggle_decision、poll_decision、scheduler_intent_after_scan、classify 都是「输入 → 输出」的纯函数，文件 I/O 和锁全部留在调用侧——所以核心逻辑可以被大量单元测试锁死。
  • 锁内部化：BackendLifecycle 的 Mutex 不对外暴露，调用方永远拿不到锁，纪律（不长持锁、不在锁里做 I/O）不会泄漏出去。
  • 平台门控：macOS 专属模块（tray / menu_model / shell_settings / shell_menu / alas_tasks / notify / control_api）全部 #[cfg(target_os = "macos")]，Windows/Linux 构建连编译都不编译它们。

它刻意没做的事

  • 不包含任何游戏逻辑、认图、调度（那是 ALAS 的事）。
  • 不注入游戏进程（控制通道通过源码补丁暴露 HTTP 接口，而不是往游戏进程里注入东西）。
  • 不做 pip 自动更新、不重启 adb（与官方 Electron 版的行为差异，见 README）。
  • 对 ALAS 的全部接触 = 6 类：环境变量、子进程、HTTP（网页 + 控制 API）、JS 注入、配置文件、源码补丁（控制 API 注入，锚点 module/webui/api/__init__.py）。

2. 双击启动器之后：内部 9 步时序

这是启动器「内部怎么执行」的主线。每一步都对应真实代码。

  1. 进程入口 main.rs。Windows 上先探测是否挂在父控制台（AttachConsole → HAS_CONSOLE 标记），后面所有子进程据此决定要不要 CREATE_NO_WINDOW（避免弹黑窗）。初始化 tracing 日志。
  2. setup_environment() 注入环境（setup.rs）。先定位 ALAS 根目录：可移植版（exe 旁有 deploy/installer.py）→ exe 目录；macOS 包 → Contents/AzurLaneAutoScript。然后 chdir 进去，往 PATH 头部注入工具链：经典可移植树是 toolkit/bin、toolkit/libexec/git-core（Windows 另有 toolkit、toolkit/Scripts、toolkit/git/cmd）；PR-5885 树没有 toolkit，改为树内 .venv/bin（Windows .venv/Scripts）——uv 托管的 python 从这里解析，git/adb 走系统 PATH。Unix 还把 toolkit/lib 塞进 LD_LIBRARY_PATH。绿色版工具链，不污染系统——之后所有 python / git 命令都靠这里找得到。
  3. 读部署配置：deploy_config::webui_port() 解析 config/deploy.yaml，取 Deploy.Webui.WebuiPort（缺省 22267，只告警一次）。这个端口是后面所有连接的「插座」。
  4. Tauri 装配（setup 闭包）：注册 save_as 命令 + 对话框插件 + 单实例插件；按 tauri.conf.json 建 main 窗口（先隐藏）并挂 on_page_load 注入器；macOS 上再建托盘（含轮询线程）和「外壳设置」菜单。
  5. Ready 事件 → 后台线程接管：注册 Ctrl-C 处理器；然后立即 backend.begin_start()——把状态机置为 Initializing。这一步在任何模式下都先做，保证初始化窗口期内托盘开关是禁用的，用户不可能在 ./config 被清理的中途点出第二个后端。
  6. 读「自动启动」门闩（macOS）：ShellSettings.auto_start_backend（默认开）；非 macOS 恒为开。决定 Ready 线程走「自动启动」还是「只准备不启动」分支。
  7. splash 窗口当进度条：text_to_splash() 把文本包成一个自包含 HTML 再 base64 成 data: URL，splash.navigate() 即可换页——不需要静态资源服务器。然后 setup_alas_repo()：先跑 ALAS 自己的 deploy.atomic.atomic_failure_cleanup('./config') 清掉上次中断的残留（详见 §5），再跑 git 更新，进度实时刷到 splash；更新完成后用 sparse-checkout 排除两个废弃壳——webapp/ 与 webapp-tauri/src-tauri/（保留 webapp-tauri 前端源码：FastAPI 网页的页面来自 webapp-tauri/dist）。随后应用控制 API 补丁（apply_patch，锚点 module/webui/api/__init__.py，详见 §8）；补丁失败只降级为进程级控制，不阻塞启动。
  8. 拉起后端（backend.start(port)）：置环境变量 ALAS_LAUNCHER_PID=启动器pid，spawn 进独立进程组——入口按树形二选一：payload 里有 gui.py → python gui.py --host 127.0.0.1 --port <端口>；PR-5885 fork 的树已删 gui.py → python -m module.cli run web --host 127.0.0.1 --port <端口> --no-open（stale-cleanup 的 argv 启发式仍只认 gui.py，是已知局限；退出注册表的组杀仍兜底）。然后每 100ms 试连 127.0.0.1:端口，最多 60 秒。连上后还要（探测工具可用时）验证端口主人是自己人（§4 端口所有权探测；工具缺失则 fail-open 跳过）——防止一个陈旧服务器占了端口还假装启动成功。另外 spawn 之前就有一步「清场」：kill_stale_alas 主动击杀上次启动器遗留的 ALAS 残留进程（10 轮 × 200ms），杀不动的幸存者或异主占口才走到「拒绝启动」（§4）。
  9. 收尾分支：成功 → 销毁 splash、main 窗口导航到 http://127.0.0.1:端口/、显示。仓库准备失败（git/清理阶段）→ splash 保留错误文本，mark_stopped 置回 Stopped 但不置 start_failed——这是「没启动成」，不是「启动失败」。后端启动失败（spawn/端口阶段）→ 状态机置 Stopped + start_failed=true，splash 保留「Starting GUI」页（stale-cleanup 类错误则导航到专属错误页），托盘显示本地化的启动失败文案。两条失败路径之后都要唤醒托盘刷新。自动启动关闭时 → 更新完仓库后同样 mark_stopped，把 main 窗口导航到本地化「已停止」页（也是 data: URL），托盘开关保持可用。
两个关键时序细节：① begin_start() 必须早于 splash 之后的一切 I/O——初始化窗口内托盘开关禁用，是「绝不双开后端」的第一道保险；② 任何 mark_stopped 之后都要显式唤醒托盘轮询线程，因为轮询的「差异门控」不把状态迁移当变化，不唤醒就会卡在「启动中…」的假渲染上。

3. 后台状态机：Stopped / Initializing / Running + 用户意图

启动器对 ALAS 后端的全部认知，浓缩成一个三态机（BackendLifecycle，backend.rs）。它把「进程管理」包装成几个带语义的动作：begin_start / start / stop / mark_stopped / mark_stopped_crashed。

图 2：后端生命周期状态机。红色回边 = 失败/异常路径，绿色 = 正常路径。
动作状态效果关键约束
begin_start() → Initializing；清 start_failed/crashed；意图 = Start；启动 TTL 时钟；记 pending_start_epoch 必须在可能很长的 spawn 之前调用——让菜单显示「启动中…」且并发点击成为 no-op（绝不双开后端）
start(port) 成功 → Running；失败 → Stopped + start_failed=true 排序契约：旧后端必须先 terminate + drop 再 spawn——因为 Drop 里的 ALAS_LAUNCHER_PID 残留清扫会杀掉任何带此标记的新进程。且全程不持锁（spawn 可等 60s，托盘轮询不能被堵）
stop() → Stopped；清所有标记；epoch += 1；进程在锁外终止 epoch 是退出竞态的解药：stop 落在 spawn 进行中时，迟到的 start 重锁后发现自己 epoch 过期，会丢弃晚产出的子进程并报 STOP_INTERVENED，绝不把退出路径覆盖成 Running
mark_stopped() → Stopped（不碰 start_failed） 用于两条「没启动成」路径——仓库准备失败、或自动启动关闭（§2 步骤 9）。「没启动成」≠「启动失败」，托盘不显示 start-failed 文案
mark_stopped_crashed() → Stopped + crashed=true 后端自己死了（端口探测失败）或外部被杀死 → 显示「异常停止」
set_scheduler_intent() / advance_intent_if_changed() 记录/演进用户意图 演进必须原子（一次锁内完成读-算-写，MINOR-1）；Start 意图 90 秒未获确认（调度器一直没起来）自动解除 → 恢复「异常停止」语义
调度器存活的判定（backend.rs 固定规则）：数 uvicorn 进程的存活子进程数——multiprocessing 的 Manager 是常驻基线（+1），调度器是第二个（+1）。存活子进程数 > 1 = 调度器活着；僵尸进程和 resource_tracker 不计。EnableReload 开时还要先找到 uvicorn 子进程本身（它在后端入口进程 gui.py / module.cli run web 监督之下），再数它的孩子。

4. 进程管理：进程组、退出注册表、端口所有权

child_process.rs + child_process/port.rs。启动器里所有子进程都走这一层——它的核心承诺是：不管怎么退出，不留孤儿进程。

机制实现防的是什么
进程组包装
spawn_with_group		 基于 command-group：Unix 上子进程 exec 前先 setpgid 自成组长；Windows 上建 kill-on-close 任务对象。返回 ManagedChild，外面永远见不到裸 child kill_group() 一条信号收掉整棵树（python + 它的 git/pip 孙进程），而不是只杀组长留孤儿
超时等待
wait_with_timeout		 100ms 轮询 try_wait，到截止时间就 kill_group + reap，返回 Err 卡死的子进程变成响亮失败，而不是 splash 永远转圈。git 更新上限 600s——单一总 deadline：无论快慢、是否还在吐进度，超时即杀（fetch + pip 装 wheels 冷启动必须在这个预算内完成）
退出注册表
register_for_exit		 静态 Mutex<Vec<pid>>。Ready 线程 spawn 的进程先登记；ExitRequested 时 kill_registered_groups() 逐个杀；完成即注销（ExitGuard Drop） 用户更新进行中关窗口 → git/pip 树被整组杀掉；注销防止 pid 回收后被误杀（pid 复用安全）
杀组重试
kill_process_group		 2 秒内循环：进程已消失 → 直接返回；否则 SIGKILL 组 + 组长，100ms 后返回；失败 20ms 重试 spawn 握手窗口期（exec 完成前 setpgid 还没跑）单发信号可能静默丢失——实测 macOS 上信号 t0 接受、t+50ms 才死透，所以退出清理不能赌时序运气
端口所有权探测
port_owner_pid		 平台命令：macOS lsof -tiTCP:port -sTCP:LISTEN；Linux ss -ltnp；Windows netstat -ano。拿到监听者 pid 后与 spawn 的组长比对进程组（Unix 比 pgid；Windows 沿祖先链上溯 64 层） 端口可能被上一个启动器实例的陈旧服务器占着——连上不一定是自己的后端活了。不同组 → 拒绝启动（「refusing to start over a stale server」；但 spawn 前 stale_cleanup 已先尝试清场，见 §2 步骤 8）。探测工具缺失 → fail-open（跳过检查但不阻塞启动，靠 Drop 残留清扫兜底）
残留清扫
ManagedBackend::drop		 先杀自己的进程组；再用 sysinfo 扫全系统进程环境变量，凡带 ALAS_LAUNCHER_PID=自己pid 的一律 kill 任何漏网的泄漏进程（比如后端又 fork 了别的东西）都会因为「环境变量血缘标记」被兜底回收——这就是为什么排序契约要求「旧 Drop 先于新 spawn」

优雅终止序列（terminate()）

  1. Unix：向整组发 SIGTERM（给后端进程优雅退出的机会）。
  2. 500ms 内每 100ms 轮询 try_wait，提前退出则直接收尾。
  3. 没退 → 告警「gui.py didn't exit, killing it...」→ kill_group()（SIGKILL 级）。

Windows 特判

  • window_util.rs：启动时 AttachConsole(ATTACH_PARENT_PROCESS) 探测是否从终端启动；没有终端 → 所有子进程加 CREATE_NO_WINDOW（不弹黑窗）；从终端启动 → 保留子进程输出可被看到。
  • Windows 上没有可查询的组 id → 端口归属用「祖先链」近似：监听者沿 parent 上溯，命中组长即自己人。
  • 退出注册表在 Windows 上只杀组长（无 job 句柄可查），但 ManagedBackend::drop 的 ALAS_LAUNCHER_PID 扫描仍兜底。

5. 仓库更新：复用 ALAS 自己的 git 逻辑 + 进度偷看

setup.rs 的 git_update 是本仓库最「取巧」的一段：它不重写更新逻辑，而是复用一个 Python 类，并偷看它的输出做进度条。

  1. 构造一段 Python 脚本：import deploy.git → 用装饰器包一层 GitManager.execute，凡是包含 ' fetch ' 且没有 --progress 的参数，就自动替换成 ' fetch --progress '——逼 git 输出进度。
  2. spawn + 登记：python -c <脚本> 走 spawn_with_group（独立进程组），并 register_for_exit 登记进退出注册表；用 ExitGuard 保证结束即注销。
  3. 偷看输出：stdout/stderr 各起一个读线程（pipe_lines），按字节流切行（含奇怪的处理：把 xx:xx 形式的进度行切出来），经 mpsc 通道送回主循环。
  4. 解析进度：含 ===== 的行 → 替换成空格显示阶段名；含 objects: / deltas: / files: 的行 → find_percentage 抠出百分比，画 50 格进度条 [==== ...]，实时推给 splash 的 status_updater。
  5. 总时限：600 秒「总」deadline（不是每行超时）——一个话多但卡死的 fetch 也会准时炸掉。超时 → kill_group + 报错「Repository update timed out」。
  6. 前置清理：更新前先跑 python -c "import sys; from deploy.atomic import atomic_failure_cleanup; atomic_failure_cleanup(sys.argv[1])" ./config——复用 ALAS 自己的原子写失败清理（同样进程组 + 超时包裹），清掉上次中断留下的临时文件。
Linux 特判：setup_git_ca_bundle() 用 openssl-probe 找到系统证书，git config --local http.sslCAInfo 指过去——绿色版 git 在 Linux 上默认找不到 CA 证书会 https 失败。

deploy_config.rs 把原先在 main.rs / tray.rs 里手写五遍的 YAML 遍历收敛成一个类型化模块，每个字段的缺省语义都和旧行为一一对应。

解析核心是纯函数 DeployConfig::from_value(Option<Value>)——不碰文件，所以「缺字段/空值/坏类型」的缺省矩阵可以拿手工构造的 JSON 做单元测试全覆盖。

7. macOS 托盘：3 秒轮询 + 差异门控 + 任务列表

tray.rs + menu_model.rs + alas_tasks.rs。这是本仓库最大的独立功能：菜单栏里直接看 ALAS 任务、一键启停调度器。

轮询线程的每一圈（poll_once）做了什么：

  1. 状态快照：读 BackendLifecycle（锁内部化，只拿拷贝）。
  2. 端口复活检查：状态是 Running 但端口 100ms 连不上 → 两连败才 mark_stopped_crashed()（一次失败可能是瞬时抖动，成功一次就清零连败计数）。
  3. 任务获取（仅 Running 时）：alas_tasks::fetch_tasks() 直接读文件——控制 API 只暴露实例状态与调度器启停，没有任务列表端点，所以托盘仍是「文件读取器」：config/alas.json（调度数据）+ module/config/i18n/<语言>.json（显示名）。时间用 date +"%F %T" 取（格式与 ALAS 的 NextRun 字符串一致，字典序 == 时间序，直接字符串比较分类）。
  4. 调度器存活探测：从后端 pid 出发做进程树扫描（§3 的 >1 规则）。
  5. 决策 + 门控：poll_decision（纯函数）算出任务区要渲染成 Degraded / Empty / Tasks 以及是否变化；只有「变化了」或「被显式唤醒」才真的 set_menu 重建——避免菜单闪烁。

任务分类规则（镜像 ALAS WebUI 的概览页）：启用的任务按 NextRun 升序排；第一个到期 = 运行中，其余到期 = 队列中，未到期 = 等待中；每组最多显示 3 条。注意这是有文档的近似——启动器没有调度器实时通道，永远把第一个到期任务当「运行中」。

开关点击（handle_toggle）的完整决策链：

  1. 去重：try_acquire_in_flight（compare_exchange 抢一个 AtomicBool）。抢不到 → 忽略并告警「上一次点击还在进行中」。守卫对象随 worker 闭包移动，所有退出路径都释放。
  2. 降级检查：ws_control_available() 为假（配了密码/SSL），或控制 API 补丁失败（patch_failed()）→ 告警并走进程级控制。
  3. 点击时刻重新扫描（不用轮询缓存）：端口探测 + 调度器进程树扫描，得到此刻的真相；端口死了 → 先 mark_stopped_crashed 再决策。
  4. 查矩阵 toggle_decision：
状态调度器存活控制 API 可用动作
Initializing任意任意NoOp（开关本来就禁用；初始化期间的二次点击直接无效——防双开第二道保险。注意初始化并非只有 60s：自动启动路径含仓库准备，可远超 60s，见 §2 步骤 7-8 与图 2）
Stopped任意任意StartBackend（整组拉起来，再视控制 API 可用性决定要不要顺带启调度器）
Running任意否StopBackend（降级模式：进程级停止，传统语义）
Running是是StopScheduler（只停调度器，WebUI 保持存活）
Running否是StartScheduler（只启调度器）
  • StartBackend → begin_start() + spawn_start_worker（专用 worker 线程跑最长 60s 的 spawn——UI 线程绝不阻塞；完成/失败后唤醒轮询，把「处理中…」替换成真实状态）。降级模式注意：API 不可用时跳过「顺带启调度器」——后端起来了但调度器保持停止，而降级后的 Running 矩阵只剩 StopBackend，托盘没有启调度器的入口，需到网页里手动启动。
  • Stop/StartScheduler → 先写意图（set_scheduler_intent，避免「调度器还没死透」的空窗闪出异常停止），再 spawn_scheduler_call 调 §8 的控制 API（5 秒超时；后端刚拉起时由 15 秒有界重试线程兜底）；失败只告警，轮询自愈。
  • StopBackend → backend.stop() + 主窗口导航到「已停止」页。
锚点失效告警：控制通道依赖 module/webui/api/__init__.py 里的两个固定锚点（create_api_app() 应用工厂，PR-5885 webui 重写引入）。每次启动 apply_patch 先校验锚点，任何不匹配 → PatchOutcome::AnchorMismatch → patch_failed() → 托盘调度器开关降级为进程级控制（降级不静默：splash 进度行与日志都会提示；托盘状态行的降级角标只反映密码/SSL 场景——状态行由 ws_control_available 驱动，不感知补丁状态）。补丁写入 fail-closed：先写 control_api.py 再写 api/__init__.py，任何一步失败都不留半补丁，下次启动重新应用。

8. 控制通道：控制 API 补丁（HTTP）

control_api.rs + patch.rs。改造前这条通道是 PyWebIO WebSocket「伪装浏览器点按钮」（已随 commit 029e95b 删除）；现在换成与网页共用同一个 ProcessManager 的 HTTP 通道——启动器每次仓库更新后往 ALAS 源码注入一个补丁，暴露调度器启停 REST 端点。注意端点是本仓库注入的，上游 ALAS 并不自带。

  1. 补丁注入（patch.rs）：锚点 = module/webui/api/__init__.py 里的两处上下文（def create_api_app() -> FastAPI: 与 app.include_router(events.router)——注入取首个匹配，当前 payload 里该行只有一处；即 PR-5885 webui 重写的应用工厂）。在锚点上方注入 import 片段、在 events.router 行下方注入 app.include_router(alas_control_router)（注册顺序讲究：文件更靠后的「/」前端 catch-all 挂载不能遮蔽 API 路由），并落一个 control_api.py 模块；以 marker 注释（# === alas-launcher:control-api ===）标记幂等。
  2. 三种结局 + 错误通道（PatchOutcome）：Applied（新注入）/ AlreadyApplied（marker 已存在，跳过）/ AnchorMismatch（锚点漂移 → mark_patch_failed() → 托盘降级进程级控制）；第四种结局走外层 Result::Err（读写失败，同样 fail-closed 置标志）。写入顺序铁律：先写 control_api.py，最后写 api/__init__.py——反过来会让 __init__ 导入还不存在的模块、把 WebUI 直接弄挂；两个文件都走 tmp + rename 原子替换（Windows 上先删目标再 rename）。
  3. HTTP 客户端（control_api.rs）：刻意零依赖的最小 HTTP/1.1 客户端——每次调用新建一条到 127.0.0.1:端口 的 TCP（connect_timeout），读写各 5 秒超时，请求头带 Connection: close，读到 EOF 为止。响应按状态码分流：200 解析 JSON / 401 → ApiError::Locked / 其它 → ApiError::Http(code)。
  4. 端点：GET /api/alas/instances（只读：实例名 + 运行状态 state 1..=4）；POST /api/alas/{name}/scheduler/start|stop（启停调度器，返回实例状态快照——启停本身是异步的，响应值可能是启停前的状态，客户端要靠后续轮询确认；未知实例名 404，防凭空创建幻影 manager）。调度器死亡检测的主信号是进程树 liveness 翻转（连续 2 拍才算数），state 1→3 迁移是附加权威信号——ProcessManager.state 对「被杀」不可靠（renderables 残留会把被杀的调度器读成 state 2）。
  5. 认证与降级：配了密码/SSL 时服务端对 start/stop 直接 401（_locked() 查 Password / WebuiSSLKey）；mutating 端点还做本机校验（_local_host()：Host 必须是 127.0.0.1 / localhost / ::1，带 Origin 时 Origin 也必须本机，否则 401）。instances 不走 _locked()（保死亡检测），但设密码时 PR-5885 的 PasswordGate 中间件包住所有路由、连 instances 一起 401——反正客户端那时也已降级。客户端侧 ws_control_available() 为假时干脆不调用，直接整组启停（进程级控制）。
  6. 调用方（tray.rs）：spawn_scheduler_call 发 api_scheduler_start/stop；后端刚拉起时由 15 秒有界重试线程（每 1.5s 一拍）兜底；失败只告警，轮询自愈。
为什么从「伪装浏览器」换成 HTTP：WS 通道脆弱——协议锁死 pywebio 1.6.2、按钮回调 ID 渲染后 1 秒内失效、点击重发会双开调度器。控制 API 的语义就是「启停调度器」本身，不再逆向 DOM；代价是依赖源码锚点稳定（锚定 PR-5885 webui 重写的 create_api_app() 工厂），锚点失效时降级进程级控制。控制通道的消费方（control_api / tray / notify 等）被 cfg(target_os = "macos") 门控在 macOS；但补丁注入本身是跨平台的——setup.rs 在所有平台都会 apply_patch，Win/Linux 也带着补丁跑，只是没有托盘去消费它。

9. 外壳设置与语言：settings.json + 原地改菜单

shell_settings.rs + shell_menu.rs。macOS 应用菜单栏里追加的「外壳设置」子菜单：检查更新 / 自动启动后端 / 语言。

项行为实现要点
持久化 ShellSettings 5 字段（language / auto_start_backend / 通知总开关 notify_enabled / notify_scheduler_death / notify_task_complete）存到 dirs::config_dir()/alas-launcher/settings.json 刻意不放进 payload 的 ./config——那个目录每次启动都会被 atomic_failure_cleanup 清掉。写入是原子写：先写同目录 .tmp + fsync，再 rename。读入是宽容解析：文件缺失 → 缺省；损坏 → 告警 + 缺省，绝不让菜单挂掉

检查更新 worker 线程跑只读 git 序列：rev-parse --abbrev-ref HEAD 取本地分支 → git ls-remote origin <该分支> 取远端头 → 对比本地 HEAD → 弹原生对话框（有更新 / 已最新 / 检查失败） 对比的是同一个分支（MINOR-3：绝不用 ls-remote origin HEAD，那会拿远端默认分支比，非默认检出时误报）。15s 超时；对话框用异步 show()——文档明确警告：blocking_show() 在 worker 线程里会死锁主线程（观察过：点「检查更新」整个 UI 卡死）

10. 退出与清理：一条不剩

ExitRequested 是启动器执行链的最后一环，也是它「管家」身份的最高体现。

触发方式路径
关主窗口WindowEvent::CloseRequested → app.exit(0) → 走 ExitRequested
托盘「退出」tray-quit → app.exit(0) → 同上
Ctrl-CReady 时注册的 ctrlc::set_handler → exit(0)（终端里跑启动器时可用）
Cmd+Q / Dock 退出（仅 macOS）NSApp terminate 只触发 RunEvent::Exit（CloseRequested / ExitRequested 都不触发）→ 调同一套 cleanup_for_exit（幂等，重复调用安全）
二次启动单实例插件：不建新进程，只把已有窗口 set_focus（不抢端口、不双后端）

ExitRequested 内部顺序（有讲究）：

  1. 先置 tray_stop=true 并同步 join 托盘轮询线程（MAJOR-4：靠 join 而不是「下一圈退出」的标志位——轮询线程在收尾前还在做无害的状态读取，绝不允许对已销毁的托盘调 set_menu，那是崩溃源）。
  2. kill_registered_groups()——杀掉更新/清理阶段登记的进程组（用户更新到一半关窗口，git/pip 树不孤儿）。
  3. backend.stop()——状态置 Stopped + epoch 自增（打断任何在途 spawn），进程组 SIGTERM → 500ms → SIGKILL；ManagedBackend Drop 里 had_child 门控的 ALAS_LAUNCHER_PID 残留清扫随 Drop 触发。
  4. 退出兜底再扫一遍：cleanup_for_exit 最后无条件做一次全系统 ALAS_LAUNCHER_PID 清扫——防 setsid 守护化的孙进程不在注册表组内、Drop 清扫又被 had_child 门控跳过的组合漏网（ALAS 目前从不 setsid，纯防御）。

12. 术语表：初级开发者速查

进程组（process group）
Unix 概念：一组进程共享一个组长。启动器用 command-group 保证每个子进程自成一组，kill 整组 = 杀组长 + 所有子孙。Windows 对应物是任务对象（job object）。
epoch
后端状态机里的代数计数器。每次 stop() 加一；在途的 start() 完成后发现代数变了，就知道自己已被打断，丢弃迟到的子进程。
SchedulerIntent（调度器意图）
启动器记录的用户最后一次调度器启停请求（None/Stop/Start）。用来区分「调度器自己死了」（异常停止）和「用户让它停的」（正常停止）。Start 意图 90 秒未获确认会自动解除。
TTL（存活时间）
这里指 Start 意图的 90 秒时钟：用户点了启动但调度器一直没起来，90 秒后意图过期，状态行恢复「异常停止」语义，不会永远显示「启动中」。
fail-open / fail-closed
安全策略术语。fail-open = 检查失败时放行（本仓库端口探测工具缺失时采用）；fail-closed = 检查失败时拒绝。选 fail-open 是因为探测工具缺失时拒绝启动比放行更糟。
sparse-checkout（稀疏检出）
git 只检出仓库部分目录的机制。启动器在每次更新后用它排除 webapp/ 与 webapp-tauri/src-tauri/ 两个废弃壳（保留前端源码），省体积也防误编译。
two-strike（两连败）
端口探测连续失败两次才判定后端崩溃，防止单次瞬时失败误报。
控制 API（control API）
启动器注入到 ALAS 源码里的 HTTP 端点集合：GET /api/alas/instances（实例状态）与 POST /api/alas/{name}/scheduler/start|stop（调度器启停，{name} 默认就是 alas，所以 §0 里写作 /api/alas/alas/…）。与网页共用同一个 ProcessManager——语义上是「正路」（不再逆向网页 DOM），但这些端点是本仓库补丁注入的，上游 ALAS 并不自带。
锚点（anchor）
补丁注入的目标上下文标记（module/webui/api/__init__.py 的 create_api_app() 定义行与 app.include_router(events.router) 行，PR-5885 webui 重写引入）。锚点不匹配 = ALAS 上游结构变了，补丁拒绝写入（AnchorMismatch）并降级进程级控制。
patch_failed / 降级
补丁写入失败或锚点漂移后置位的全局标志；托盘开关与「重启后端」据此退回进程级控制（整组启停），不再尝试控制 API。
muda
Tauri 2 的菜单库。其菜单项句柄是 Arc 包装的原生项——这正是「菜单建一次、之后原地改文字/勾选」可行的原因。
data: URL
把整个 HTML 页面 base64 编码后塞进 URL 的协议。启动器的 splash 和停止页都是这么渲染的——不需要任何静态资源服务器。
resource_tracker
Python multiprocessing 的辅助进程。进程树扫描时它被排除，否则会被误当成调度器（基线 +1 就变 +2）。
差异门控（diff gate）
托盘轮询只在检测到变化时才重建菜单，避免每 3 秒闪一次。代价是「状态迁移不算变化」，所以任何状态迁移后都要显式唤醒轮询。
本报告基于 alas-launcher 仓库当前源码（main 分支）逐文件梳理生成，与《alas-architecture-guide.html》互为姊妹篇：那份报告展开 ALAS 本体，这份只讲启动器仓库内部执行。图中文件名/函数名/常量名均可直接在仓库中检索验证。
