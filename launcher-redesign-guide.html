0. 先看结论：这次改造到底改了什么

30 秒速览。对照《ALAS Launcher 内部执行图解》，本报告只回答一个问题：目标架构下哪些模块变了、怎么变的。

改造前，启动器里最重的一块是 「伪装浏览器」控制通道：托盘要启停调度器时，逆向 PyWebIO 的 WebSocket DOM 协议，找到网页上的「开始/停止」按钮并模拟点击。它全项目最脆弱——版本锁死 pywebio==1.6.2、按钮回调 ID 渲染后 1 秒内失效、点击重发会双开调度器，代码里塞满了 HOME_QUIESCE、CONFIRM_WINDOW 之类的竞态补丁。

改造后，这条通道被换成 一条官方路径镜像的 HTTP 控制 API：给 ALAS 打一个 60 行的小补丁（新增 control_api.py + 在 4.3 年没动过的 fastapi.py 里挂一行路由），托盘直接调 ProcessManager.start()/stop()——和网页按钮调的是同一个函数。同时新增 macOS 原生通知（带开关）。

一句话总结：改动 = 三处：①删掉「伪装浏览器」DOM 黑客（pywebio.rs ~750 行 + tungstenite）；②换成「控制 API 补丁 + 轻量 HTTP 客户端」（新增 ~160 行）；③新增 macOS 原生通知（调度器异常死亡提醒默认开、任务完成默认静默）。其余全部保持现状——启动流程、环境注入、git 更新、进程组、WebView 嵌入、发布流程，一根手指都不动。

2. 三处改动逐项对比

改动就三处。第一处是重头（删 + 换），第二、三处是纯新增/微调。逐项看。

改动 1 控制通道：DOM 黑客 → 控制 API 补丁

维度改造前 · pywebio.rs 伪装浏览器改造后 · 控制 API 补丁
机制 逆向 PyWebIO WebSocket DOM 协议，模拟点击网页按钮 HTTP POST 调 ProcessManager.start()/stop()——与网页按钮同一函数
协议依赖 锁死 pywebio==1.6.2，版本漂移即失效（版本守卫告警） Starlette Route，与 pywebio 版本无关
竞态处理 HOME_QUIESCE 6s、CONFIRM_WINDOW 1.5s、callback id <1s 时效、js_yield 应答、重发双开 普通 HTTP 请求/响应，天然无这些竞态
代码量 pywebio.rs ~750 行 + tungstenite 依赖 control_api.py ~60 行（上游补丁）+ Rust HTTP 客户端 ~100 行
对接锚点 webui DOM 结构（活跃 churn，2026-04 还在改） module/webui/fastapi.py（2022-04-14 起 4.3 年未动）
失败语义 告警日志后照点（可能静默失败） 补丁应用失败 → fail-closed 降级禁用，不阻塞启动
为什么敢这样换：补丁不发明新机制——它把 ALAS 官方 gui.py --run 路径（app() → args.run → on_startup → restart_processes）原样暴露成 HTTP。改的是「怎么叫」，不是「叫什么」。

改动 2 macOS 原生通知（纯新增）

事件检测方式默认
调度器异常死亡 控制 API state 突变（API 不可用时退回现有 uvicorn 子进程观测） ON 唯一默认打扰——调度器死了不跑任务，必须让用户知道
任务完成 config/alas.json 的 NextRun 前移 diff + i18n 任务名 OFF 静默（绝大多数时候不需要打扰，用户可自行打开）
手动启停 — 不通知 纯噪音
  • 开关shell settings 新增：全局开关 + 按事件类型开关（调度器事件 / 任务完成）
  • 检测复用 macOS 托盘已有 3s 轮询循环做 diff，零新依赖
  • 平台macOS-only：通知依赖托盘常驻——Win/Linux 无托盘 = 关窗即退进程，通知无从谈起

改动 3 macOS 托盘：唯一变化是控制走 API

托盘部件是否变化
任务列表（读 config/alas.json + i18n，3s 轮询）不变
菜单结构 / i18n / 状态行不变
调度器启停开关变化：WS DOM 点击 → HTTP 调控制 API（改动 1 的消费方）
Win / Linux 门控（cfg(target_os = "macos")）不变——Windows 放弃扩展，Linux 后议

3. 一根手指都没动的部分

约束（用户明确）：不维护 ALAS 上游改动。所以改造被严格限制在「启动器 ↔ webui 之间的一条缝」里。

启动器侧保持：

  • 环境注入（PATH / LD_LIBRARY_PATH / ALAS_LAUNCHER_PID）
  • git 更新流程（复用 ALAS 自身 deploy.git.GitManager）
  • 进程组 / 端口所有权 / 退出注册表
  • 后台状态机（Stopped / Initializing / Running）
  • 主窗口 WebView 嵌入 + saveAs JS 注入
  • 单实例 / splash / 退出清理
  • 发布流程（手动 releases，CI 悬置）

ALAS 侧保持：

  • pywebio 网页本体（WebView 内容原样）
  • ProcessManager 语义（17 个月未动的 API）
  • 调度器子进程模型（multiprocessing）
  • 配置格式 config/alas.json（多年稳定，托盘已直读）
  • 不做任务失败检测（日志解析，格式随上游 churn）
  • 不做上游优化（cnocr/mxnet 换代、requests 升级——违背约束）
原则：只动「启动器怎么叫 ALAS」这一条缝。ALAS 本体作为一个自包含 Web 服务方块，前后完全一致。

4. 为什么敢打补丁：稳定面实证

约束的落地方式：只对接 ALAS git 历史中长时间未改动的部分。以下为 2026-08-13 对真实 payload 的 git log -1 实证。

对接面最后改动稳定时长结论

module/webui/setting.py2023-02-083.5 年State.manager / deploy_config
module/webui/process_manager.py2025-03-1717 个月API 调用面（start/stop/get_manager/state）

5. 降级与失败语义

新架构的每个失败路径都有明确的降级出口，原则：宁可降级，不可破坏。

场景行为
补丁锚点校验失败 / 应用失败fail-closed：托盘调度器开关禁用 + 提示；不阻塞启动、不损坏仓库
控制 API 不可达（密码 / SSL / 未打补丁）降级为现有进程级控制（现状行为，托盘状态行已有「仅进程级控制」提示先例）
通知发送失败静默，不 crash
调度器死亡检测误报通知内容含降级文案；检测窗口对齐现有 uvicorn 子进程观测

6. 删除清单与新增清单

账目要清楚：删了什么、加了什么、净变化多少。

删除（改造前）

  • pywebio.rs ~750 行：WS 连接、DOM 解析、按钮定位、js_yield 应答、竞态处理
  • tungstenite 依赖（Cargo.toml）
  • pywebio 版本守卫（requirements.txt 解析 + 1.6.2 校验）
  • HOME_QUIESCE / CONFIRM_WINDOW / READ_POLL 等时序常量与相关测试

新增（改造后）

  • module/webui/control_api.py ~60 行（上游补丁，新文件永不冲突）
  • Rust HTTP 控制客户端 ~100 行
  • 补丁应用器：锚点校验 + 应用 + fail-closed（含单元测试）
  • 通知模块：3s 轮询 diff + 事件分发 + shell settings 开关

净变化：Rust 约 −650 行；Python 上游补丁 +60 行（仅装入启动器二进制，不落地 payload 之外的任何地方）。

7. 数据流对比：一次「启停调度器」

同一次用户操作，改造前后的路径差异一目了然。

改造前（7 步，每步都可能碎）

  1. 托盘点击 → 读 requirements.txt 校验 pywebio==1.6.2
  2. 建立 WS 会话（/?app=index），等 6s quiesce
  3. 应答 js_yield（localStorage / visibilityState）否则 DOM 不渲染
  4. 定位 aside 实例按钮 → 点击
  5. 定位 menu Overview 按钮（--menu-Overview-- 标记）→ 点击
  6. 定位 scheduler_btn 按钮（callback id <1s 时效）→ 点击
  7. 观察 1.5s 标签翻转确认；绝不重发（会双开调度器）

改造后（2 步）

  1. 托盘点击 → POST /api/alas/alas/scheduler/start
  2. control_api.py → ProcessManager.get_manager("alas").start(None, updater.event) → 子进程拉起
同一函数：网页上的「开始」按钮回调就是 self.alas.start(None, updater.event)——API 与网页殊途同归，行为 100% 一致。
通知数据流（新增）：轮询循环 3s 读 config/alas.json（diff NextRun 前移）+ 控制 API state 突变 → 事件 → 查 shell settings 开关 → tauri-plugin-notification 弹通知。任务完成默认静默（OFF），调度器异常死亡默认打扰（ON）。

10. 术语表

fail-closed
补丁锚点校验失败时，托盘调度器开关禁用 + 提示，而不是继续用旧方式硬试——宁可降级，不可破坏。
稳定面锚点
ALAS git 历史中长时间未改动的文件/API，是对接补丁的唯一允许位置。实证：fastapi.py 4.3 年。
官方路径镜像
补丁不发明新机制，只是把 ALAS 官方 gui.py --run 的 ProcessManager 调用链原样暴露成 HTTP。
控制 API 补丁
新增 control_api.py + fastapi.py 注入一行，启动器 git 更新后自动应用，锚点校验失败即降级。
调度器异常死亡
唯一默认打扰的通知事件：调度器进程非预期消失（控制 API state 突变 / uvicorn 子进程观测），意味着任务停摆。
NextRun diff
任务完成检测：config/alas.json 的 Scheduler.NextRun 前移 = 任务跑完，触发通知（默认静默）。
