GIT_UPDATE_TIMEOUT = 600s justification
  The update script runs gm.git_install() = ALAS-history fetch + pip wheel
  install. On a cold cache / slow link that exceeds 300s; the timeout only
  converts a wedged child into a loud Err instead of a splash hang, so a
  generous ceiling costs nothing (Momus ADVISORY-2). The git_update wait is a
  TOTAL deadline (recv_timeout with remaining = deadline - now), not per-line:
  a chatty but wedged fetch still fires.

Fail-open justification (port_owner_pid)
  Tool missing/unparseable -> None -> that start SKIPS the ownership check.
  Acceptable because: the existing ALAS_LAUNCHER_PID residue scan in
  ManagedBackend::Drop still reaps same-launcher stale processes; only a
  server left by ANOTHER launcher instance slips through on that rare path;
  lsof is near-universal on macOS (primary target). Fail-closed would break
  startup on machines without the tool — worse than the hole it plugs. One
  warn! per failed probe.

Deviations (justified)
  1. spawn_with_group returns Result (plan wrote `-> ManagedChild`).
  2. Registry: unregister_for_exit + kill_registered_groups added to the
     planned register_for_exit (pid-recycle safety; ExitRequested hook).
  3. Port-ownership split into src/child_process/port.rs (250-LOC ceiling:
     combined file was 353 pure LOC; lifecycle 218 + port 143, both clean).
  4. kill_process_group retries briefly + settles 100ms (measured macOS
     spawn-handshake signal race — see RED->GREEN trace).
  5. Windows exit-kill kills the registered leader via sysinfo (no queryable
     job handle from a pid); launcher exiting anyway; backend children
     covered by the ALAS_LAUNCHER_PID Drop scan. Documented in module.
  6. Linux/Windows cfg paths compile-checked only on macOS (no cross
     targets installed); APIs used (nix getpgid/kill, sysinfo process/
     parent/kill, command_group) are platform-stable across the crate set.
  7. Tray uvicorn count tests are timing-sensitive (3s poll, kill -9 race,
     pre-existing design); observed 2 flaky failures in one parallel run out
     of 7 full runs, pass in isolation and in 5 consecutive full runs. My
     tests spawn only sleep/sh (no python), counted per parent-pid, so they
     cannot be counted by tray's scan; residual flake is pre-existing load
     sensitivity, not a logic regression.
