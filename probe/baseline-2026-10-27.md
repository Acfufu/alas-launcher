# 附录 A：scrcpy 截图链路试验（trial v2，2026-10-27）

**结论：scrcpy 1.20（payload 唯一捆版）在 Android 16 模拟器上三堵墙全灭，非补丁可救；截图链路可行动杠杆仍是 raw screencap（见基线第 2 条）。**

试验台 `probe/bench_scrcpy.py`：monkeypatch `ScrcpyOptions.command_v120` 置 `control=false` +
空闲 control 占位连接，其余跑真 payload 栈（Scrcpy + PyAV 解码）。三轮实测：

| 尝试 | 结果 | 机制 |
|---|---|---|
| ① stock（control=true） | server 启动即崩 | Android 16 上 server 端 Device 初始化剪贴板监听 `NoSuchMethodException IClipboard.addPrimaryClipChangedListener`（trial v1 已知） |
| ② control=false，只建 video 连接 | 握手死锁，30s 零字节 | scrcpy 1.20 `DesktopConnection.open` **无论 control 与否都 accept 两条连接**（video→control）；dummy byte 在第一条后发，设备 meta 与 H.264 流在两条都建立后才开始。缺第二条连接 → server 永久阻塞在第二个 `accept()` |
| ③ control=false + 空闲 control 占位连接 | 握手全通（设备 meta 68B 到达、分辨率 1280×720、编码器 `c2.android.avc.encoder` 分配成功），随后 server 死亡，30s 零帧 | **API 36 移除了 `SurfaceControl.createDisplay(String,boolean)`**。scrcpy 1.20 `ScreenEncoder` 反射调用即 `AssertionError`，logcat 实锤：`E scrcpy: java.lang.AssertionError: java.lang.NoSuchMethodException: android.view.SurfaceControl.createDisplay [class java.lang.String, boolean]` |

游戏前台动画正常（双截屏哈希比对确认），排除了"静态画面编码器不出帧"假设。

附带发现（已修复）：
- `AzurLaneConfig` 每次 `setattr` 都会写盘，注释"memory only"是错的——首轮 bench 把部署
  `config/alas.json` 的 `ScreenshotMethod` 落成了 `'scrcpy'`（部署版 scrcpy 即墙①，等于给部署埋雷）。
  已用 payload 配置 API 改回 `'ADB'`，bench 改为快照 + finally 恢复。
- scrcpy server 的 CleanUp 守护进程在 spawn 时 CLASSPATH 指向不存在的 `/data/local/tmp/scrcpy-server.jar`
  （payload 只推带版本号的 `-v1.20.jar`）→ `ClassNotFoundException` → ART abort。对 server 本身无影响，
  仅意味着断连后无守护清理（payload 自身 init 时的 server stop 流程兜底）。

出路（按成本排序）：raw screencap 立即可用；scrcpy 需升级 server 到 2.x（协议/代码大改，payload 无捆版），
或改走 droidcast(MJPEG)；两者都超出"补丁"范畴。

# 附录 B：P4 ANE 复验（静态 N 模型，2026-10-27）

**结论：上午的假设证实并已打通——挡 ANE 的是动态 W，不止是动态 N。全静态形状（N=1、W=640 定宽）
的 CoreML 路径实测落 ANE：ANE Power 稳定 ~311 mW（median 311 / max 314，60s 相位内无跌零）；
仅静态 N + W 桶化仍为 0。**

方法：`run_p4_admin.sh`（powermetrics 2s×90 包住 40s idle + 60s × 2 负载相位；首轮因脚本少 shift
掉 `--` 分隔符导致 bench 未启动，数据作废重跑）。条件同基线：游戏前台、ALAS webui 空闲。

| 相位 | 模型 / 形状策略 | ANE mW (median) | ΔCPU mW | infer p50 | ops/s | parity |
|---|---|---|---|---|---|---|
| P4s_staticn | staticn：N=1 静态，W 动态 + 64 桶 | 0 | +1602 | 4.64ms | 117 | true |
| P4s_static640 | staticn_w640：N=1、W=640 全静态，全部 pad 到 640 | **311** | **+1144** | 8.02ms | 122 | true |

解读：
- 静态 N 单独不够：staticn 相位 ANE 仍恒 0，W 也必须静态——与"CoreML EP 对含动态维度的子图
  不落 ANE"的行为一致（GetCapability：staticn 51/60 节点 3 分区；w640 49/52 节点 2 分区）。
- ANE 路径的 CPU 功耗增量低 ~450 mW（+1.14W vs +1.60W），吞吐持平（122 vs 117 ops/s）。
- fixed640 对小 crop 是 5-30× 的 pad 浪费，但 ANE 吞得下：相位内 p50≈avg（8.0/8.2ms，无长尾）；
  空闲系统冒烟时 p50 3.38ms。staticn+bucket 相位内 p50 4.64ms 更快但分布双峰（avg 8.5ms）。
- 模型：out/azur_lane_staticn_w640.onnx（3.4MB，签名 [1,1,32,640]→probs[160,39]）。

对上午杠杆排序的修订：
- 杠杆 3（ANE 化 OCR）从"需重导出才有路"升级为"已打通、实测落 ANE ~311mW"。但收益量级结论不变：
  ALAS 真实节奏（每秒个位数推理）总收益 ≤0.3W，价值主要在削线程尖峰。若 payload 决定采纳：
  dev_tools/ocr_convert 重导出全静态 W=640 版 + al_ocr.py 推理前统一 pad 到 640。
- 杠杆 2（截图链路）：scrcpy 1.20 已判死（附录 A），raw screencap 为唯一近期可动项。
